# Multi-Agent 运行时

目标方案：[Iris Multi Agent Design](https://q0kyes8lnt5.feishu.cn/wiki/SVz6w01hui1eKekTFqbcLHEinXg)。主 Agent 通过能力注册表委派任务，领域实例隔离上下文与工具，业务动作仍经确定性权限检查与任务级人工确认。

实现按模块推进：任务/能力契约与 PG 存储；主从调用与确认恢复；领域接入、入口开关及本地集成评测。高级后台事件调度、按事实依赖选择性重规划和生产资格评测另有验收要求，不能仅凭固定模型测试宣布完成。

`goals`、`tasks`、`agent_states` 的 DDL 见 [schema.sql](../db/schema.sql)。新增协作关键状态不回退内存；状态更新检查 revision 并与稳定身份的审计事件同事务提交。测试中的内存存储仅为 test double。SDK 会话 checkpoint 与业务操作记录有不同职责，恢复期间不能把一个已开始副作用的调用直接重跑。

RunBudget 由主从请求共用，限制前台模型/Jev、工具、子任务恢复次数、token、上下文大小和执行时间。未返回模型 usage（包括 Jev）时显式标记不完整；并发调用、后台长期记忆提炼及服务端计费存在边界，不能据此声称精确费用上限。跨多轮长目标的持久预算将在后台任务阶段补齐。

## 受控预览

在 `.env` 中显式设置 `MIO_MULTI_AGENT_ENABLED=true` 后重启，`/chat` 由主 Agent 处理。默认仍关闭，保留原单 Agent 入口。开启时初始化 `goals`、`tasks`、`agent_states`；数据库故障会停止协作执行，不回退到空状态继续操作。现有记忆表 `events` 也必须已存在。

主 Agent 只有发现、委派、查看、继续和取消任务五种工具。三个领域各有独立技能视图与工具目录；主 Agent 不直接拥有 MCD、腾讯或微博业务工具。新增领域通过 `DomainDefinition` 注册，核心运行时没有品牌路由分支。当前主模型负责协调、标准模型负责领域执行，Jev 用于领域写操作意图审核；沿用原入口时保留原有路由。

领域 Agent 使用实际 `ReActAgent` 和 `ChatService` 权限恢复链，完成或补问分别通过任务控制工具明确结束。内部委派消息不进入长期记忆，Jev 的授权依据固定为主会话真实用户表达。主 Agent 只记录真实主对话；受控画像读取仅包含全局和当前领域页，不隐式触发额外检索模型。

每次人工确认在服务端关联子任务、子会话、原调用 id、递归冻结的参数、参数指纹和工具契约指纹；客户端仍只提交不透明确认编号和布尔决定。默认五分钟过期，真正发出业务请求前再次检查有效期和指纹。批量工具调用允许逐次记录决定，但该子任务全部调用都已决定后才恢复。普通全局消息会保守地使旧待批准任务变为 STALE；显式定向回答只更新对应任务，不使无关的有效审批失效。任务绑定领域技能目录的内容哈希，版本改变不能恢复旧任务。全局消息尚未按事实依赖做选择性失效。

PREPARE 任务不能执行写操作。REQUEST_APPROVAL 仍受原权限、Jev 与人工轨约束；不可逆操作在真正提交前再次检查批准及契约。副作用开始前持久化操作标识和参数指纹。缺少可信核验器或有效证据时，写调用返回后仍为 UNCONFIRMED、任务为 UNKNOWN，不能凭框架 SUCCESS 或模型文本宣称业务已成功。一项任务最多提交一个外部写操作，同会话同领域已有未核查提交时不再创建写任务，仍可创建 PREPARE 任务查单。已接入的结构化回执核验与阶段边界见下文。

SDK checkpoint 已存 PG；恢复 RUNNING 任务时不会重跑旧调用，而将其归类为中断/UNKNOWN 后要求核查。NEEDS_INPUT 和有效 AWAITING_APPROVAL 可以通过各自路径恢复；检查点缺失或损坏时停止恢复。同领域操作在目标行锁保护的事务内检查历史提交并落下操作记录，再联系供应商，避免多个待批准任务绕开重复提交限制。后台事件队列、跨 HTTP 请求的长时自主执行、按依赖局部重规划，以及正式生产资格评测尚未交付；当前是前台请求内的主从协作预览，限单应用进程使用，尚未实现多副本下的主会话 checkpoint 并发控制。未知结果不得用新任务、新会话或切回旧入口作为自动重试手段。

## 本地验证

`./scripts/eval.sh` 保留全部离线基线，并执行新增主从和权限回归；不使用 `.github` 或模型密钥。集成测试运行真实主 Agent → 任务工具 → 真实领域 ReActAgent → 人工确认 → 子会话恢复 → 主会话结果回传，只将模型、存储和业务服务替换为 test double。

`JdbcPersistenceTest` 验证真实 SDK 消息多态序列化、损坏检查点拒绝恢复、乐观锁冲突与审计失败回滚。它使用模拟 JDBC 边界，不冒充真实数据库验证。提供测试库的 `MIO_TEST_PG_URL`、`MIO_TEST_PG_USERNAME`、`MIO_TEST_PG_PASSWORD` 后运行 `./scripts/mvn.sh -B -Dtest=JdbcPostgresIntegrationTest test`，可验证 PostgreSQL 行锁竞争、事务回滚及跨存储实例读取检查点。测试自行创建随机 `mio_eval_*` schema，结束后只删除该 schema；没有连接配置时实库测试显式跳过。

页面按任务展示状态和独立决定按钮；待确认期间仍可补充新要求。重新打开页面和请求出错后会回读服务端任务状态，不自动批准或重跑。完成前台请求前无法通过同一个聊天输入打断；取消 API 可以阻断任务后续工具，已经发出的外部请求则保留 UNKNOWN。界面验收使用隔离 HTTP fixture，不触达真实服务。

## 操作核验闭环

操作账本保存在任务 JSON 的 operations 中，与任务版本、审计事件同事务更新。OperationOutcome 与 TaskStatus 分离：UNKNOWN 任务可以接收晚到回执，但不能重新执行。回执按内容指纹去重、追加保留，证据冲突回到 UNKNOWN。写入回执时锁定任务行，取消和并发回执不会覆盖彼此。旧 JSON 缺少 outcome/receipts 时保持未知，兼容既有状态。

核验器仅由可信应用配置注册，模型和客户端没有提交“核验成功”的接口。当前腾讯创建订单适配器仅在实际桥接返回的退出码、HTTP 状态、业务码和字符串订单号均有效时确认创建已发生；这不证明派单、支付或履约完成。核实后解除运行时同领域的不确定性阻塞，供应商自身的进行中订单保护仍生效。框架默认的 RUNNING 状态也可能只是未设置状态，是否核实仍完全取决于供应商证据；ERROR/DENIED 等状态不能通过该核验路径。

其他工具、畸形或冲突回执保持未知，没有根据失败码推导“未执行”。未收到可关联回执的超时操作仍保持阻塞，查单对账、跨会话资源互斥和供应商幂等键尚待后续接入。一次任务发出操作后不能继续等待新操作的审批或补问，后续动作需要新的任务并再次经过授权边界。

运行 `./scripts/eval-postgres.sh` 可用 PostgreSQL 16 临时容器执行完整离线入口。容器只绑定本机随机端口、不挂载业务数据，退出时清理；使用已有测试库时仍可设置 MIO_TEST_PG_*。实库覆盖同领域提交竞争、审计失败回滚、检查点恢复及并发晚到回执，模型和业务服务始终使用 test double。

## 结构化事实交接

TaskSummary.facts 提供带来源任务、证据编号、版本、观测时间及有效期的事实。当前仅从持久操作账本的已核实创建回执投影业务资源编号，类型为 provider_resource_reference；原始回执和版本在 PG 中持久保存，事实视图按需重建。编号证明资源曾创建，不证明当前状态、可用性或履约结果，因此它没有时效性状态的过期语义。ETA、库存、报价等短时事实需要独立的可信提取器和有效期规则，尚未接入。

主 Agent 在 delegate_task 的 inputs 中引用 taskId、factId、version、alias，来源必须同时出现在 dependencies；不能传一个自定义值代替引用。运行时校验会话、目标版本、来源完成状态、事实存在性和版本，再将实际值交给领域 Agent。模型文本和框架 COMPLETED 本身均不会生成事实。未绑定 inputs 的任务仍兼容旧契约；运行时不能从自由文本推断某任务是否遗漏了必要输入，后续应通过能力输入契约进一步约束。

每次工具调用及提交前复核事实。PG 提交事务还锁定来源任务并重新校验，避免读取事实之后、写操作记录之前发生证据变更。当前来源证据产生冲突时事实消失，下游工具被阻断，晚到完成结果也不能覆盖为成功。此处只实现已声明依赖的有效性检查；全局事实修订、主动选择性失效和局部重规划仍待后续阶段。

## 任务级补问与回答恢复

NEEDS_INPUT 任务返回 questionId，绑定任务编号、任务 revision 和问题文本。客户端通过 `/chat` 提交 message 与 taskReply（taskId、questionId），不提交伪造的任务状态、授权或问题文本。服务端核对会话与问题版本，将原始回答、问题及时间写入任务 answers，并与 task_answer_received 审计事件同事务提交。回答只进入对应领域 Agent 的授权上下文，不写入全局目标、不进入主会话长期偏好提炼；不扩大 PREPARE 范围，也不能代替实际工具调用的人工批准。

回答提交后先进入 INPUT_READY，再恢复原子会话。若在这两步之间中断，页面或主 Agent 可以通过恢复入口继续已经保存的回答；`/chat` 的 resumeTaskId 仅接受 INPUT_READY，不重跑运行过、已完成或已提交副作用的任务。恢复、定向回答、批准互斥提交。取消、目标变更或技能版本改变会阻断旧恢复路径，数据库中的旧 JSON 缺少新增字段时按空回答历史读取。

普通消息保留单补问兼容路径：收到消息时恰好只有一个待回答任务才记录候选归属。多个任务同时提问时必须明确选择，不能在其他任务完成后把原先含糊的消息重新分配给剩余任务。普通消息仍属于全局用户表达并触发保守失效，需要避免无关审批失效时应使用定向回答。此处实现路由与版本绑定，尚未为问题定义日期、地点等字段类型或自动判断回答语义是否充分。
