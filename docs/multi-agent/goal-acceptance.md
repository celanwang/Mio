# 目标级证据验收闭环

本次收尾目标是把用户明确选择的验收范围、任务输出契约和可信业务事实连接起来。系统可以确定性回答“已确认范围是否满足”，不再用任务循环结束或模型的成功声明代替目标验收。范围由用户确认，评估由运行时执行；确认条件不会产生业务授权，也不会创建、恢复或重放任务。

## 使用方式

启用多 Agent 后，目标区域展示验收状态。在“设置或修改验收条件”中选择需要验收的任务，按需要添加字段限制，再点击“确认这些验收条件”。可在任务等待执行或批准时先确认条件；真正的业务写入仍通过原有确认卡片单独批准。只有工作报告、没有可信证据契约的任务不可作为达成条件。

当前出行契约提供预计行程耗时（秒）、行程距离（米）和创建后的资源编号。数值支持等于、不超过、不低于，同一字段可以组合上下限；文本只支持相等。字段和单位由能力实现注册，不能由模型或工具文本自行创建。当前没有把报价列表中的最低金额当作成交总价，也没有用订单编号证明支付、司机接单或履约；其他供应商需接入自己的可信事实及契约后才能提供相应验收字段。

界面展示每项条件的证据范围、比较值与未满足原因。保存后的条件持久化于 PG，刷新页面和进程重启不丢失；浏览器不保存可直接恢复的满足结论。清除条件必须显式操作并检查版本，空条件返回尚未定义，不将空集合判为全部成功。关闭目标后可读取原条件与证据，不再允许修改条件；暂停、恢复和条件确认都不改变累计预算。

## 状态与边界

| 状态 | 含义 |
| --- | --- |
| NOT_DEFINED | 尚未确认条件，或用户明确清除了条件 |
| STALE | 用户意图版本已改变，需要重新规划并确认当前任务 |
| PENDING | 仍有未完成条件，或确认条件虽已满足但当前版本还有待处理任务 |
| PARTIALLY_SATISFIED | 一部分确认条件满足，其余仍需处理 |
| NOT_SATISFIED | 当前证据不足、字段不匹配、依赖失效或契约变化 |
| BLOCKED | 该目标存在未知业务操作，包括旧意图版本遗留的操作 |
| SATISFIED | 所有确认条件当前满足，当前版本没有未结束任务，且没有未知业务操作 |

目标控制状态 ACTIVE/PAUSED/CLOSED 与验收状态分开保存和展示。SATISFIED 不自动关闭目标、不取消外部订单，也不代表确认范围之外的自然语言要求已经全部实现。普通全局用户表达改变意图版本后，旧验收条件变为 STALE；定向回答和业务批准不被伪造成新意图。旧版本未知操作继续阻止整体满足，只有原有可信核查链能够解除它。晚到回执可提供证据，历史中断状态及禁止重放规则保留。

评价只消费当前可信事实，检查来源任务、目标版本、能力及输出定义指纹、输入依赖、证据有效期和字段值。数值使用 BigDecimal，接受最多三十位整数和十二位小数的有限十进制表达；NaN、Infinity、未注册字段或无法核验的值不能通过。报价到期后重新评估，不把过去成立的条件永久缓存为满足。

## 接口与存储

`GET /api/tasks?sessionId=...` 的响应增加 acceptance，包含确认记录、可选契约、逐项评估、阻塞原因、检查时间、最早证据到期时间及任务版本。主 Agent 只有 `read_goal_acceptance` 读取工具，没有确认、修改或清除条件的工具。该工具沿用已有工具预算，普通页面回读只访问本地 PG，不调用模型或供应商。

人工界面通过 `PUT /api/tasks/goal/acceptance` 提交 sessionId、expectedGoalRevision、expectedControlRevision、expectedRevision 和 selections。每项选择提供 taskId、从候选项读取的 contractVersion 及 checks；字段条件为 fieldId、operator 和 expected。清除需明确提交空 selections，缺少列表或版本返回 400，目标或条件版本冲突返回 409，数据库不可用返回 503。响应丢失后先回读，不自动重复提交。

goal_acceptances 每个目标保存一份带 schemaVersion 的当前条件，确认版本单调递增。确认按租约、目标、任务的既有顺序加锁，条件与 goal_acceptance_confirmed 审计事件同事务提交；审计失败则全部回滚。服务端重新验证任务归属和可信契约，忽略任何“模型已经同意”的文字。条件确认不追加用户表达、不签发业务批准、不撤销当前执行代次、不预占模型或业务读取预算。

独立回读使用可重复读事务；在已有执行围栏事务内则沿用围栏保护，读取同一目标及单次任务集合。每次从源记录重新计算结论，记录损坏或未来未知 schemaVersion 不能降级为成功。字段定义进入契约和能力指纹，新增或修改字段会使旧能力版本任务不能继续沿用原批准，升级仍需停止旧进程，不能混合运行新旧版本。

客户端同时检查目标意图版本、控制版本、确认版本、检查时间和任务版本，拒绝旧响应覆盖新状态。发起新对话或控制请求时撤下旧结论；成功结论最多展示三十秒，短期证据更早到期时提前撤下，并扣除请求耗时。可见页面到期后只回读本地状态，隐藏页面等待重新聚焦；这不是后台自主执行。编辑草稿在重绘时保留，多个字段限制不会在再次保存时悄悄丢失。

## 验收证据

`GoalAcceptanceTest` 覆盖确定性比较、到期边界、意图变更、部分满足、未完成工作、旧版本未知操作、晚到证据和不可信值。`GoalAcceptanceApiTest` 检查参数、错误反馈和模型只有读取工具。`JdbcGoalAcceptanceIntegrationTest` 在隔离 PG 验证重启恢复、并发确认、审计回滚、跨会话拒绝、暂停关闭和预算、批准、租约不变。

`JdbcOrchestrationAcceptanceTest` 将用户确认条件接入实际主从 SDK 循环：先查询报价并绑定分析，再确认验收范围，最后单独批准或拒绝创建。确认范围时模型调用、业务写入、意图和待批准卡片均不改变；批准后按关联证据满足条件，拒绝后不产生资源，也不能判为全部满足。主 Agent 通过真实的只读工具读取评估结果。

`node --test scripts/test-goal-acceptance.mjs` 执行实际前端模块，覆盖响应乱序、证据到期、编辑重绘、上下限保留、响应丢失后回读、切换会话、关闭后只读、单位显示和发起操作时撤下旧结论。该入口由 Python 检查集调用，因此完整验收需 Node.js 18+；可通过 MIO_NODE_PROGRAM 指定可执行文件。运行 `./scripts/eval-postgres.sh` 完成六类 PG 套件和全套离线门禁，未提供 PG 或缺少客户端检查运行条件时不能宣称完整通过。

本次不调用付费模型或真实供应商。自然语言意图的自动完备性判断、未接入供应商的履约证据、后台自治和生产资格仍需独立证据，不能从离线成功或 SATISFIED 推导。
