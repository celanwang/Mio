# 点餐条件分支

仅阅读当前任务相关的部分。继续使用主技能的最终报价、当前订单授权和结果核实规则。

## 新增配送地址

已有地址不满足需求时，先收集真实城市、联系人姓名、联系电话、地址及门牌号。缺失信息询问用户，不能用示例值或脱敏电话号码创建地址。核对内容并通过现有审批流程批准后调用 `delivery-create-address`。使用成功返回的新地址 ID 查询可配送门店；失败时保留用户已提供信息，不自动反复创建。

## 领券及积分兑换

- 查看已有券按需使用 `query-my-coupons`；决定本次能否使用，仍以当前门店、取餐方式和时间下的适用券为准。
- 用户希望领券时，先用 `available-coupons` 查看可领内容。`auto-bind-coupons` 会领取当前可领的一批券，不能描述成只领取指定单张券；说明实际作用后走项目审批。领取成功后重新查当前门店可用券，再算价。
- 用户明确希望用积分兑换时，用 `query-my-account` 查积分，`mall-points-products` 查商品，按需用 `mall-product-detail` 查规格。明确兑换商品、数量和积分或其他费用，通过审批后用 `mall-create-order` 执行兑换。虚拟券与实物配送要求按当前工具定义处理。
- 兑换成功不意味着已经点餐：查明返回券能否用于本次门店和场景，更新购物车再算价。兑换订单与普通点餐订单分别保存，不能把商城订单号交给普通点餐查询工具。
- 用户只说“便宜一点”“有优惠吗”时，先查询和比较；是否领券、消费积分或增加会员卡等收费项目，根据用户实际意图和本次授权处理。

## 营养目标

用户给出热量或营养要求时，用 `list-nutrition-foods` 辅助筛选。按实际名称、份量和数量匹配数据，不能把数据库里有的餐品当成门店必然可售。数据缺失或匹配不清时说明不确定性，不生成精确的虚构营养总值。选餐后继续套餐细节、算价和确认步骤。

## 企业团餐

仅在用户有团餐需求时进入此分支，常见场景为 `orderType=2, beType=6`。确定真实配送地址、门店和所需预约时间后，用 `query-meal-assistance` 查询适用服务；选择用户需要的服务，保存返回的 `gmServiceCode`。相关服务与费用带入对应算价和下单步骤，摘要中说明助餐服务和收费。

## 取消已创建订单

先用已知订单号核实具体订单；不明确时借助 `order-list` 确认。询问或沿用用户已明确的取消原因，按当前 schema 映射取消原因编码；其他原因不能冒充未提供的具体原因。说明即将取消的订单，通过现有审批后调用 `cancel-order`。以业务返回确认取消结果，必要时再查询状态；不能承诺任何订单都可取消、一定退款或具体到账时间。拒绝取消授权后保留订单，不换一个调用重新取消。

## 错误及恢复

| 情况 | 处理 |
|---|---|
| 没有可用门店、门店不支持预约 | 向用户提供真实可行的地址、方式或时间调整；没有结果就说明，不编造门店 |
| 餐品无货或套餐选项失效 | 获取当前菜单或详情，提供真实替代，修改后重新算价 |
| 券失效或不适用 | 刷新适用券并重新报价；不能默默换成更贵的订单直接创建 |
| HTTP 成功但业务失败 | 检查成功标志、错误说明和关键字段，按实际失败处理 |
| 创建响应超时或没有明确订单结果 | 先查单或历史订单；不能因为网络失败直接重发创建请求 |
| 取消响应超时 | 先查询订单核实取消状态，再决定是否需要用户继续处理 |
| 认证失效或服务不可用 | 说明连接问题；恢复后重新核实报价和订单状态，不使用旧批准直接执行 |
| 后端重启或旧审批失效 | 按项目提示建立有效会话、恢复必要信息；重新报价和确认实际创建请求 |

不要在恢复过程中添加永久授权，也不要把“继续”“重试查询”等表达扩大为批准新增地址、消费积分、创建或取消订单。
